# Метрики тестирования

Скрипт `tools/metrics.py` берёт данные из `docs/bug_reports.md`, истории git и `coverage.json`.

```bash
pytest --cov=src --cov-branch --cov-report=json -q
python tools/metrics.py
```

## Результаты

| Метрика | Значение | Как считается |
|---------|----------|---------------|
| Покрытие операторов и ветвей | **100.0%** (цель ≥ 80 %) | coverage.py, `--cov-branch` |
| Найдено дефектов | **9** | число разделов `## BUG-n` в `docs/bug_reports.md` |
| Размер кода | 575 строк (SLOC) | строки `src/` без пустых и комментариев |
| Плотность дефектов | **15.7 на 1000 строк** | дефекты / (SLOC / 1000) |
| Среднее время обнаружения дефекта (MTTD) | см. ниже | минуты от тега `testing-start` до коммита «Тест BUG-n …» |
| Mutation score | **97.8%** (до ревью — 87.0%) | убитые мутанты / все мутанты |

## Среднее время обнаружения дефекта

Метка `testing-start` ставится в начале тестирования, а коммит «Тест BUG-n …» фиксирует момент,
когда дефект воспроизведён. В учебном прогоне инструкции команды выполнялись подряд, поэтому
скрипт показал 0.18 мин — это число не отражает реальной работы. **Запустите
`python tools/metrics.py` в своём репозитории и подставьте свои значения:**

| Дефект | Время обнаружения, мин |
|--------|-----------------------:|
| BUG-1 … BUG-9 | _из вывода вашего запуска_ |
| Среднее | _из вывода вашего запуска_ |

## Анализ

- Покрытие намного выше требуемых 80 %, но само по себе оно не доказывает качество — проверка
  мутациями показала пробелы, закрытые в ходе ревью.
- Плотность 15.7 дефектов на 1000 строк высока для небольшого проекта: код ЛР №1–3 проверялся
  только «счастливым путём» и несколькими ошибочными вводами; граничные значения и предположение
  об ошибке нашли то, что обычные тесты пропустили.
- Дефекты BUG-1, 3, 4, 6 найдены анализом граничных значений, BUG-2, 5, 7, 8, 9 — предположением
  об ошибке: методы дополняют друг друга.
- Метрики следует пересчитывать после каждого выпуска, чтобы видеть тенденцию.
