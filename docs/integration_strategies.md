# Сравнительный анализ стратегий интеграции (уровень 3)

## Таблица стратегий

| Стратегия | Суть | Преимущества | Недостатки | Когда применять |
|-----------|------|--------------|-----------|-----------------|
| Поэтапная (одновременная, «большой взрыв») | все модули объединяются в конце разработки | не нужны заглушки и драйверы; просто для очень малых систем | ошибки находятся поздно, трудно локализовать причину | прототипы, 2–3 крошечных модуля |
| Инкрементная | модули добавляются по одному с тестированием на каждом шаге | ошибки локализуются быстро; всегда есть работающая версия | требует планирования порядка и вспомогательного кода | почти любые проекты |
| Нисходящая | сначала верхние модули, нижние — заглушки | ранняя проверка архитектуры и интерфейсов; работающий «скелет» с первого шага | нужны заглушки; нижние модули тестируются поздно | чёткая иерархия модулей, важны интерфейсы и сценарии использования |
| Восходящая | сначала нижние модули, для них — драйверы | нижние (часто критичные) модули проверяются рано; не нужны заглушки | программа как целое появляется поздно; нужны драйверы | сложные библиотеки, вычислительное ядро, много переиспользуемых модулей |
| Сэндвич | одновременно сверху и снизу, затем середина | параллельная работа команд; сочетает плюсы нисходящей и восходящей | сложнее планировать; нужны и заглушки, и драйверы | большие системы с несколькими слоями |
| Риск-ориентированная | первыми интегрируются самые сложные и рискованные модули | риски снимаются рано | остальные модули ждут; нужна оценка рисков | внешние интеграции, новые технологии, высокая цена ошибки |
| Функционально-ориентированная | интеграция по функциям системы, а не по модулям | рано готова законченная пользовательская функция | модули затрагиваются многократно | продукт с независимыми сценариями использования |
| Т-образная | сначала вертикальный «срез» через все слои, затем расширение | рано проверяется архитектура «насквозь» | остальные части откладываются | новые системы с неопределённой архитектурой |

## Рекомендации по выбору

| Тип проекта | Рекомендуемая стратегия |
|-------------|--------------------------|
| Небольшое консольное приложение с центральным управляющим модулем (наш проект) | нисходящая |
| Библиотека или вычислительное ядро | восходящая |
| Крупная многослойная система, несколько команд | сэндвич |
| Проект с внешним нестабильным сервисом или новой технологией | риск-ориентированная |
| Продукт, поставляемый по пользовательским сценариям | функционально-ориентированная или Т-образная |
| Учебный прототип из двух-трёх модулей | инкрементная или даже поэтапная |

## Почему в проекте выбрана нисходящая

Наш конвейер «ввод → обработка → вывод» имеет явный управляющий модуль и три простых нижних модуля.
Нисходящая интеграция позволила сразу зафиксировать интерфейсы (`Matrix`, `ProcessingResult`, `Report`,
исключения), получить работающий конвейер на заглушках и затем заменять заглушки настоящими модулями,
проверяя систему после каждого шага. Дополнительный уровень — REST-транспорт — встроился без изменения
управляющего модуля, потому что он получает функции извне.
